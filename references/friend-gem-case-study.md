# Completed Case Study：MaaHappyFish「好友摸宝」任务

这个案例展示一种比“开贝壳”更完整的协作方式：用户只提供基于记忆的业务描述，执行 Agent 负责逐步实机探索，高能力模型根据每一轮现场证据校准假设，最终形成可长期运行的确定性 MaaFramework Pipeline。

案例来源：[`zhimaheiye/MaaHappyFish`](https://github.com/zhimaheiye/MaaHappyFish)

稳定基线：

```text
6369811  feat(friend): 新增好友水族箱摸宝巡访与产物收取自动化
867ddeb  feat(friend): 捕获并补充长尾系统弹窗模板与 44 分钟 E2E 实测指标
```

最终实现以 `867ddeb` 为准。

---

## 1. 起始需求：用户只提供“可能不准确的记忆”

用户最开始只确认了大致业务规则：

```text
从好友列表第一个好友开始
→ 进入好友水族箱
→ 每次进入都检查可能出现的欢迎弹窗
→ 在好友鱼缸里收取会跟着鱼移动的产物
→ 每位好友最多处理若干次，V1 先以 12 次作为安全上限
→ 通过右上角“下一位”连续切好友
→ 最后进入加好友页面时结束整个任务
```

同时用户明确提醒：

> 这些描述来自记忆，未必完全准确，需要通过一步一步截图和实机操作验证。

因此开发时把用户记忆视为：

```text
业务方向 / 探索提示
```

而不是：

```text
已经验证的 UI 事实
```

这是整个案例最重要的前提。

---

## 2. Start Contract

最终功能明确约束：

> **必须在「我的星级好友」列表页面顶部开始任务，并确保第一排好友卡片可见。**

V1 不负责从自己的鱼缸自动导航到好友列表。

正式任务只负责：

```text
点击第一位好友
→ 巡访好友水族箱
→ 收取产物
→ 跳过耗尽好友
→ 切到下一位好友
→ 到达好友末尾后结束
```

这一设计避免把“进入好友系统”的额外导航状态无必要地塞进核心状态机。

---

## 3. 第一张好友列表截图：显眼视觉 ≠ 业务特征

第一轮截图中，部分好友卡片右上角存在明显的金色装饰角标。

高能力模型一度把它列为“可能与可收取产物有关”的待验证特征，但用户根据实际游戏经验明确指出：

```text
这个角标只是装饰
≠ 是否有产物
≠ 是否应该进入该好友
```

因此它被立即从候选业务条件中移除。

这里验证出一条重要规则：

> **视觉上最显眼的元素不一定具有业务意义。用户已有的可靠领域经验，应优先于 AI 对截图做出的视觉联想。**

---

## 4. 异常页面也可能是有效样本：鱼资源未加载

进入第一位好友后，网络原因导致大量鱼显示为黑色问号占位，但鱼头上的金色气泡仍正常出现。

这个页面没有被简单丢弃为“异常截图”，而是作为一个正式 visual variant 记录：

```text
FriendTank
└─ variant: fish_assets_unloaded
```

随后使用项目中已有模板：

```text
assets/resource/image/金币气泡.png
```

直接对好友鱼缸做 TemplateMatch。

即使鱼本身未加载，模板仍能大量高分命中气泡。这说明目标视觉与鱼模型资源基本解耦，反而证明了旧模板具有很强的跨场景复用价值。

---

## 5. 不根据模板命中就直接宣布业务成立

第一位好友中，`金币气泡.png` 可以稳定匹配，但最初只点击一个目标后：

```text
当前页面左侧“12 剩余”没有立即变化
没有明显收益飘字
只出现“存档中...”
```

如果仅凭当前画面判断，很容易得到错误结论：

```text
“金币气泡不是摸宝目标”
```

但切换到下一位好友后，服务器状态刷新，金币与剩余次数发生变化，证明前一次点击实际已经生效。

这暴露了一个非常重要的事实：

> **UI 数字可能不是实时状态。动作成功与否不能总依赖同一页面上的即时数字刷新。**

对于网络游戏尤其需要区分：

```text
本地静态显示
vs
服务器同步后的真实状态
```

---

## 6. 局部状态不能误判成全局终态

探索过程中进入一位此前已经被用户处理过的好友，左侧显示：

```text
灰色闪电
0(0点刷新体力)
```

一度可能被理解成“今日摸宝体力全部耗尽，整个任务应该结束”。

用户随后补充：这位好友之前可能已经被自己点过。

继续对其它好友实测后确认：

```text
X 剩余
```

属于当前好友自己的局部配额。

因此：

```text
FriendGemExhausted
≠ TaskDone
```

而应该是：

```text
FriendGemExhausted
→ FriendGemNextFriend
```

真正的全局结束仍然由好友末尾的加好友页面决定。

这是本案例的关键建模经验：

> **看到“0 / exhausted / 无剩余”等状态时，先判断它的作用域是当前对象、当前页面、当前轮次，还是整个任务，不要仅凭文案强度推断全局终止。**

---

## 7. OCR 识别业务语义，不绑定恢复时间

好友体力耗尽时，文案可能是：

```text
0(0点刷新体力)
```

也可能因为当前时间不同显示：

```text
0(12点刷新体力)
```

对本任务而言，真正稳定的业务含义只有：

```text
刷新体力
```

所以最终配置采用：

```text
expected = "刷新体力"
```

而不是写死 `0点` 或 `12点`。

这与“开贝壳”的 OCR 分框案例共同验证了同一原则：

> **OCR `expected` 应选择决定业务状态的稳定最小语义片段，避免把变化数字、时间或装饰文本一起绑定进去。**

---

## 8. 单目标高精度时序实验

为了确认点击一个气泡后是否会在原地残留并导致重复点击，执行 Agent 选择与其它目标距离大于 110 px 的孤立气泡，并进行了高频抓帧：

```text
0.00s：模板匹配 score = 0.9595
+0.25s：原位置 score = 0.1528
+0.65s：原位置 score = 0.4060
+1.20s：附近已有其它带泡鱼游入
```

结论：

> 成功点击的气泡会在 0.25 秒内快速消失，不会长期留在原位置导致同一目标被连续误点。

因此正式节点采用：

```text
post_delay = 500ms
```

它不是拍脑袋设置的等待时间，而是建立在实机时间序列上的安全余量。

---

## 9. 安全 ROI：不要为了“全覆盖”把 UI 也纳入模板搜索

好友鱼缸四周存在大量固定 UI：

```text
左侧金币 / 体力信息
右侧菜单
顶部好友切换按钮
底部状态区域
```

虽然 `金币气泡.png` 本身匹配效果很好，但全屏搜索会无谓增加误触风险。

经过前 1～5 位好友跨 NPC / 真实玩家背景回测，正式收取区域收窄为：

```text
ROI = [230, 140, 820, 470]
threshold = 0.75
```

该区域集中在水族箱中央开阔水域。

最终 200 个水族箱长链路测试中，气泡匹配置信度范围：

```text
0.7658 ~ 0.9845
```

没有发生对左侧 HUD 或边缘按钮的误触。

这里的原则是：

> **移动目标不一定要求搜索整个画面。只要目标会持续移动，保守的安全 ROI 往往比“全覆盖”更可靠。**

---

## 10. 每好友 12 次采用“硬保护”，不解析易变数字

用户记忆中不同好友可能存在 12 / 10 / 5 等不同档位。

V1 没有尝试 OCR 并解析所有数字，而是采用：

```text
每好友最多执行 12 次气泡点击
```

原因：

- 12 是已知最高档；
- 当前好友若已经完全耗尽，可由 `刷新体力` 直接跳过；
- UI 数字已经被证明可能存在刷新时机问题；
- 先保证确定性闭环，再考虑减少少量无效尝试。

同时明确区分：

```text
attempts
= Pipeline 成功执行过多少次“识别气泡 → Click”

不是：
获得了多少金币
不是：
实际消耗了多少服务器体力
```

因为气泡可能重叠，一个点击可能同时影响多个产物。

---

## 11. 运行时状态职责分离

为了让 Recognition 与 Action 共享计数状态，同时避免 `my_reco.py` 与 `my_action.py` 循环导入，最终新增：

```text
agent/runtime_state.py
```

共享状态：

```python
friend_gem_state = {
    "attempts": 0,
    "max_attempts": 12,
    "current_friend_index": 1,
}
```

职责严格拆分：

```text
InitFriendGemStateAction
→ 显式初始化

RecordFriendGemAttemptAction
→ attempts += 1

CheckFriendGemLimitReco
→ 只判断 attempts >= max_attempts
→ 不产生自增副作用

ResetFriendGemAttemptsAction
→ 切换成功后清零 attempts
→ friend_index + 1
```

尤其避免了把“初始化新任务”偷偷塞进某个不一定会被调用到的 Recognition 中。

## 12. 最终状态机

稳定版核心 Pipeline：

```text
FriendGemTask
  InitFriendGemStateAction
        ↓
FriendGemEnterFirstFriend
        ↓
FriendGemFriendRouter
  ├─ FriendGemAddFriendPage
  │      └─ FriendGemDone
  │
  ├─ FriendGemWelcomePopup
  │      └─ Close → Router
  │
  ├─ FriendGemSpecialPopup
  │      └─ Close → Router
  │
  ├─ FriendGemExhausted
  │      └─ FriendGemNextFriend
  │
  ├─ FriendGemAttemptLimitReached
  │      └─ FriendGemNextFriend
  │
  ├─ FriendGemCollectBubble
  │      ↓
  │   FriendGemRecordAttempt
  │      └─ Router
  │
  └─ FriendGemNextFriend
         ↓
      FriendGemResetAttempts
         └─ Router
```

核心识别条件：

```text
FriendGemAddFriendPage
OCR: "全部添加"
ROI: [750, 330, 160, 70]

FriendGemExhausted
OCR: "刷新体力"
ROI: [60, 220, 260, 120]

FriendGemCollectBubble
TemplateMatch: 金币气泡.png
ROI: [230, 140, 820, 470]
threshold: 0.75
post_delay: 500ms

FriendGemNextFriend
TemplateMatch: 好友_下一位.png
ROI: [1140, 50, 130, 80]
threshold: 0.70
post_delay: 1200ms

FriendGemSpecialPopup
TemplateMatch: 绿色勾选按钮.png
ROI: [760, 420, 120, 120]
threshold: 0.8
```

其中 `FriendGemWelcomePopup` 保留为首访好友可能出现的欢迎提示防护，但截至该版本的完整长跑仍未获得真实样本，应明确标注为“骨架待覆盖”，不能与已经验证的特殊系统弹窗混为一谈。

## 13. 分层验收：不要从单点直接跳到 200 个对象

这个案例最终形成了很清晰的测试梯度。

### 第一层：单点实验

验证一个动作的真实因果：

```text
点一个孤立气泡
→ 是否真正生效
→ 是否消失
→ 多久消失
→ 页面数字是否实时更新
```

### 第二层：5 位好友短跑

验证状态机的局部循环：

```text
初始化
→ 12 次上限
→ 切好友
→ attempts 清零
→ Exhausted 0 点击跳过
→ NPC / 真人背景兼容
```

短跑结果中，核心断言全部通过。

### 第三层：完整长链路 E2E

冻结当前实现，不再边跑边优化，完整遍历直到全局终态。

最终实测：

| 指标 | 结果 |
|---|---:|
| 总访问水族箱 / 好友数 | 200 |
| 正常采集好友数 | 198 |
| Exhausted 直接跳过 | 2 |
| 气泡匹配 score | 0.7658 ~ 0.9845 |
| 下一好友按钮 score | 0.7510 ~ 1.0000 |
| 未知稳定异常 / 卡死 | 0 |
| 金币净增长 | +597,637 |
| 连续运行时间 | 2645.3 秒 / 44.1 分钟 |

完整长跑的价值不仅是证明“能一直跑”，还在第 200 位水族箱捕获了短测试始终没有出现的低概率系统弹窗。

---

## 14. 长尾弹窗：长跑不是重复短跑

第 200 位水族箱首次出现真实系统提示：

```text
进化鱼特效已被关闭，在【设置-进化鱼特效】一栏中可打开哦。
```

执行 Agent 保存现场后，将右下绿色确认按钮固化为：

```text
assets/resource/image/绿色勾选按钮.png
```

并新增：

```text
FriendGemSpecialPopup
```

回到 Router 后继续处理当前好友。

这证明：

> **长链路 E2E 的意义不是“把短跑多执行几遍”，而是覆盖低概率状态、长时间网络波动和只有深链路才会出现的视觉分支。**

同时必须保留证据分层：

```text
FriendGemSpecialPopup
= 已实机验证

FriendGemWelcomePopup
= 用户确认可能存在，但本次 200 水族箱 E2E 未触发
```

不能因为“有一个弹窗节点已经跑通”就声称所有弹窗分支都完成覆盖。

## 15. 三方协作的升级策略

这个案例中，用户进一步授权执行 Agent：一般技术问题不必每次回来询问用户，可以先把证据交给高能力模型审核。

最终形成适合复用的 Escalation Policy：

```text
实机事实未知
→ 执行 Agent 自己截图 / OCR / 测试

技术判断未知
→ 截图 + 日志 + 当前节点交给高能力模型

业务语义未知
→ 高能力模型确认确实需要用户决策后，再询问用户
```

例如：

```text
“这个 ROI 应该多大？”
→ 技术问题，交给高能力模型

“这个按钮究竟应选左还是右？”
→ 业务规则，需要用户

“点击以后页面到底发生了什么？”
→ 实机事实，执行 Agent 应自己采样
```

这样用户不需要持续充当两台 AI 之间的人工路由器。

## 16. 这个案例最终验证出的开发原则

1. 用户的模糊记忆可以作为探索入口，但不能直接当 UI 真相。
2. Start Contract 要明确任务从哪里开始，以及脚本明确不负责什么。
3. 显眼视觉元素不等于业务特征；领域经验可以否决 AI 的视觉联想。
4. 异常页面也可能是高价值 visual variant，不要自动丢弃。
5. 模板高分命中只证明“看到了目标”，业务效果仍需单点因果实验验证。
6. UI 数字可能延迟刷新，不要把“画面没变”直接判成动作失败。
7. 局部 Exhausted 与全局 Done 必须分开建模。
8. OCR 应识别稳定业务语义，而不是绑定会变化的时间和数字。
9. 移动目标可以通过高频抓帧测量消失时延，再据此设 `post_delay`。
10. 安全 ROI 比无脑全屏覆盖更重要。
11. 计数器应记录 Pipeline 能确定的事件，不假装知道服务器实际收益数量。
12. Recognition 尽量保持纯判断；状态变化由明确 Action 驱动。
13. 开发测试应分为单点实验、短跑、完整长链路 E2E。
14. 不要为“可能出现的弱网问题”提前堆复杂 Verify；真实失败出现后再按证据增加保护。
15. 长跑可以发现短跑永远遇不到的低概率状态。
16. 已验证分支与仅有骨架/用户记忆的分支必须在文档中明确区分。
17. 实机事实、技术判断、业务决策应该由不同角色负责升级。

## 17. 为什么这个案例特别适合作为 Skill 示例

“开贝壳”案例主要展示：

```text
状态机修正
OCR 分框
visual variants
完整轮次计数
```

而“好友摸宝”进一步展示：

```text
用户只给模糊业务记忆
→ Agent 自主逐步采样
→ 高能力模型持续局部校准
→ 单点实验验证因果
→ 状态作用域判断
→ 移动视觉目标时序测试
→ 安全 ROI
→ 共享运行时状态
→ 5 位短跑
→ 200 水族箱 / 44 分钟 E2E
→ 捕获第 200 位才出现的长尾弹窗
```

它完整体现了本 Skill 的核心目标：

> **把便宜执行 Agent 用在机械的实机观察与验证上，把高能力模型用在真正需要状态建模、证据判断和架构取舍的地方，最终让运行时回归确定性的 MaaFramework Pipeline。**
