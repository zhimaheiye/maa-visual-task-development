# 现场 Bug 采样与排错规范

本文件用于 Pipeline 已经进入实机测试后发生失败时的处理。

## 1. 第一原则：先保留现场，再修

遇到失败时不要立刻：

```text
加 on_error
扩大 timeout
改固定坐标
增加新模板
同时放宽 ROI / expected / threshold
```

先保留证据。

至少记录：

```text
失败节点
预期状态
实际状态
现场完整截图
OCR 原始结果
bbox / score
当前 recognition ROI
最近日志摘要
关键参数
第一次错误动作发生的时间点
当前 task_id / completed 等状态（若适用）
```

---

## 2. 本地图片如何交给远端模型

远端模型通常看不到执行 Agent 本地路径，例如：

```text
D:\project\debug\on_error\xxx.png
```

只发送路径是不够的。

若图片不含敏感信息，执行 Agent 应优先把图片本身注入当前聊天，并附简短上下文：

```text
失败节点：OpenShellOctopus
预期：点击左侧保留按钮
实际：OCR 超时
截图时间：19:37:34
```

已经验证可行的自动化方式包括：

```text
系统剪贴板 + 模拟真实 Ctrl+V
DataTransfer File 自动化挂载
```

发送后应等待远端模型确认图片可见，再继续视觉分析。

---

## 3. OCR 分框问题

不要只看“屏幕上人眼看到一句完整文字”。

必须看 OCR 的实际结果框。

例如：

```text
视觉按钮：保留一个随机奖品
OCR： [保留] [一个随机奖品]
```

若配置：

```text
expected = 保留一个随机奖品
```

可能完全无法命中，因为没有任何单一 OCR box 包含完整字符串。

优先修法：

```text
在目标 ROI 内选择
单个 OCR box 中稳定存在
且足够唯一的最小语义片段
```

例如：

```text
expected = 随机奖品
```

不要无意义缩短为过于泛化的：

```text
奖品
继续
确定
```

除非 ROI 已经足够严格且不存在歧义。

---

## 4. ROI 边界截断：先确认输入有没有被裁坏

这是独立于 OCR 分框的另一类高频故障。

典型现象：

```text
完整画面 OCR：0(0点刷新体力)
节点 ROI OCR：0(0点刷新体
```

如果完整目标 bbox 是：

```text
x = 108 ~ 393
```

而节点 ROI 是：

```text
[60, 220, 260, 120]
右边界 = 320
```

那么最后的字符在送入 OCR 之前就已经被裁掉。

此时：

```text
expected = 刷新体力
```

必然失败。

### 标准排查

同时拿到：

```text
全屏 OCR 原始文本 + bbox
节点 ROI OCR 原始文本 + bbox
节点 ROI 的四个边界
```

比较：

```text
目标 right 是否接近 / 超出 ROI right
目标 bottom 是否接近 / 超出 ROI bottom
```

如果全屏 OCR 完整而 ROI OCR 稳定缺字，优先怀疑 ROI 截断，而不是页面加载慢或 OCR 模型随机波动。

### 正确修法

```text
确认 ROI 截断
→ 局部扩大 ROI
→ 保留原来稳定的 expected
→ 异常样本回归
→ 正常样本反向回归
```

### 反模式

不要因为 ROI 裁掉了“力”，就把：

```text
expected = 刷新体力
```

直接削弱成：

```text
expected = 刷新
```

这可能只是把漏检换成未来更难发现的误报。

## 5. 同一状态的多视觉布局

失败并不一定意味着出现了新业务状态。

先问：

```text
业务上是不是仍然应该做同一个动作？
```

例如结算页：

```text
变体1：只有“太好了”，按钮居中
变体2：“分享” + “太好了”，后者偏右
```

两者业务上都属于 Finish。

优先：

```text
记录 variant
→ 比较 bbox
→ 局部扩大统一 ROI
```

而不是立即增加两个 Finish 节点。

---

## 6. 局部校准原则

如果主状态机已经正确，而失败点只是：

```text
ROI 太窄
expected 太长
动画略慢
```

只修这一层。

不要因为一个识别 Bug 推翻已经跑通的整条状态机。

并尽量一次只改变一个主要变量，否则即使回归成功，也很难知道究竟是哪项修改真正解决了问题。

---

## 7. Timeout / 时序问题

识别失败后超时，不代表 timeout 一定太短。

先确认：

```text
目标其实出现了吗？
完整画面 OCR 有没有读出来？
ROI OCR 有没有读出来？
读出来的文本是否被 expected 过滤掉？
ROI 是否完整覆盖 bbox？
页面是否真的尚未稳定？
```

只有确认识别条件本身正确，只是页面确实更慢以后，再调 timeout / delay。

高频连续采样很适合区分：

```text
加载竞态
vs
稳定的 ROI / recognition 配置错误
```

如果 0.5s、1s、2s 后都以相同方式缺同一个字符，通常就不应该继续用“再多等一会儿”解释。

---

## 8. 固定坐标不是默认救火方案

如果 OCR 已经准确给出目标框，应优先点击识别结果。

固定坐标适合：

- 没有任何可靠识别结果；
- 页面布局高度固定；
- 经过实测确认；
- 且风险可控。

不要因为一次 OCR expected 写错就退化为硬编码坐标。

---

## 9. 日志要能解释分支

对于局部终态、跳过和保护分支，建议增加明确日志。

例如：

```text
[好友摸宝] 当前好友体力已耗尽，跳过气泡采集
```

用户再次反馈异常时，可以快速区分：

```text
Recognition 根本没命中
vs
Recognition 已命中，但后续状态机仍执行错误动作
```

不要让日志只写模糊的“成功”或“失败”，而没有说明是哪一个业务判断成功。

---

## 10. 测试次数策略

开发阶段优先：

```text
单点因果实验
→ 少量对象短跑
→ 完整长链路 E2E
→ 用户实际使用验收
```

不要一上来设置 200 次，再用长跑来发现最基础的状态遗漏。

同时也不要把长跑通过误解成所有视觉 variant 都已经覆盖。

某个 Exhausted 样本在两个好友上成功，只证明这两个现场成功。

---

## 11. Agent 回归与用户验收

技术修复完成后，执行 Agent 应继续自主完成本地回归，不需要因为普通 ROI / OCR 修改频繁打断用户。

只有功能达到：

```text
Candidate Ready
```

才停下来请用户真实使用。

```text
Agent Verified
≠ User Accepted
```

用户可能最终接受一个仍有小概率已知问题、但已经明显改善的版本。

此时应记录：

```text
Known Limitation + User Accepted
```

而不是写成 `100% Fixed`。

---

## 12. 推荐失败报告模板

```text
## 失败节点
FriendGemExhausted

## 预期
识别“刷新体力”并跳过当前好友

## 实际
Exhausted 未命中，Router 落入 CollectBubble 并误点

## 完整画面 OCR
0(0点刷新体力)
bbox=[108,226,285,46]

## 节点 ROI OCR
0(0点刷新体
bbox=...

## 当前配置
expected=刷新体力
roi=[60,220,260,120]

## 现场截图
<直接附图>

## 日志摘要
FriendGemExhausted Failed
→ FriendGemAttemptLimitReached Failed
→ FriendGemCollectBubble Succeeded
→ Click
```

这种报告通常已经足够让高能力模型区分时序问题、OCR 分框问题和 ROI 截断问题，并做局部诊断。
